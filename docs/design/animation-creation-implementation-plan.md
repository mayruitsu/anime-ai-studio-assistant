# 実装計画：会話で3Dアバターを作り、ポーズ・アニメーションをつけて動画にする

作成日: 2026-09-08
対象：`self-model-experiment` ＋ `anime-ai-studio-assistant`（2リポジトリ横断）

## 0. ゴールとスコープ

**ゴール**：4方向イラストから3Dアバターを作り、会話しながらポーズ付け・アニメーション化し、動画として書き出す、という一連の体験を実現する。

**今回のスコープ外**（別途検討）：
- 背景・エフェクトの追加
- 複数カット／シーンをつなぐタイムライン機能
- 2アプリの統合（ページ分割によるアプリ一本化）

これらは「アニメーション作成」というゴールが達成できてから、改めて別の計画として検討する。

---

## 1. 全体アーキテクチャ

```
[self-model-experiment]                      [anime-ai-studio-assistant]
 イラスト4枚 → SMPLフィッティング              VRM読み込み → ポージング/キーフレーム
 → 陰影による詳細化 → VRM書き出し              → AIモーション生成（motion-api）
         │                                            │
         └────────────────────┬───────────────────────┘
                               ▼
                  会話アシスタントサービス（新設・共有）
        ┌───────────────────────────────────────────┐
        │  汎用対話モデル（OLMoをファインチューニング）  │
        │        ↓ 必要に応じてツール呼び出し           │
        │  限定的な自作モデル（意味解析・構造化編集）    │
        └───────────────────────────────────────────┘
                               ▼
         ツール群（各アプリの機能をAPI経由で呼び出せる形に）
```

技術詳細（SMPLパイプラインのステージ設計、モデルの学習方針、ツール一覧）は`self-model-experiment/docs/design/smpl-template-pivot.md`を参照。本計画書は**実装の順序・依存関係・マイルストーン**に焦点を当てる。

### トラックB：ツールAPI化＋橋渡し（`anime-ai-studio-assistant`）

現状、`BonePoser.jsx`・`KeyframeRecorder.jsx`・`MdmPlayback.jsx`の処理はすべてブラウザ内のReactコンポーネントがVRMオブジェクトを直接操作している。会話アシスタント（バックエンドサービス）からこれらを呼び出すには、**バックエンドとブラウザ間の橋渡し**を新たに設計する必要がある（今回新たに判明した論点）。

| ステップ | 状態 | 備考 |
|---|---|---|
| バックエンド↔ブラウザの橋渡し方式の設計（WebSocket等） | ✅ | `/ws/tools`（WebSocket）＋`POST /tools/call`によるリレー方式で実装（PR #50） |
| 橋渡しの実装・疎通確認 | ✅ | `get_current_pose`・`set_bone_rotation`で実際に往復動作を確認済み（PR #49, #50, #51）。会話アシスタント（トラックD）は未着手のため、確認は`/tools/call`への直接HTTPリクエストによるもの。2026-09-08にPlaywright＋実際のVRMファイルによる実ブラウザでのエンドツーエンド検証も追加実施し、ポーズ変更がレンダリングに反映されることを確認済み |
| 既存機能のツール化（`add_keyframe`, `clear_keyframes`, `export_keyframe_video`, `load_vrm_model`, `start_motion_generation`, `get_motion_generation_status`, `play_and_export_generated_motion`） | ✅ | PR #53〜#57で完了。`generate_motion_from_text`はMDM生成に2〜3分かかるため、開始/状態確認/再生を分けた非同期ジョブ方式に設計変更した |

**小計：約5〜7セッション** → **完了**（トラックB全体）

### トラックD：会話アシスタントサービス（新設）

予備調査として、`allenai/OLMo-2-0425-1B-Instruct`（約14.8億パラメータ）をWindows側のCPU環境でダウンロード・ロード・生成まで動作することを2026-09-08に確認済み（生成に約2.2秒、GPU不要）。ただしファインチューニング前の素の状態では自己認識を誤る（「OpenAIです」と回答）等、品質面の課題がそのまま残っており、ファインチューニングの必要性を裏付ける結果となった。

| ステップ | 見積もり | 備考 |
|---|---|---|
| サービスの土台構築（OLMoのロード、推論環境） | 1〜2セッション | `motion-api`と同様のFastAPI構成を踏襲。ロード・推論の実現性は確認済み（上記） |
| ツール呼び出し基盤の実装（ツール定義→モデルへの提示→呼び出し結果の受け渡し） | 2セッション | |
| ファインチューニング用対話データの作成 | 2〜4セッション | ツール一覧確定後に着手。データ量次第で変動 |
| OLMoのファインチューニング実行・評価 | 2〜3セッション | 計算資源・反復回数に依存 |
| トラックB・Cのツールとの結合 | 1〜2セッション | |

**小計：約8〜13セッション**

## 5. マイルストーン（区切りの目安）

1. **M1**：SMPLパイプラインが1人分の写真で最後まで通り、VRMが出力できる（トラックA完了）
2. **M2**：会話なしで、既存UI操作から生成したVRMを`anime-ai-studio-assistant`で読み込み・ポーズ付けできる（トラックA・B結合）
3. **M3**：簡単な1つのツール呼び出しが会話経由で動作する（トラックB・Dの橋渡し疎通確認） 🔄 トラックB側（`/tools/call`を直接叩いての疎通）は2026-09-08に確認済み。トラックD（会話アシスタント自体）が未着手のため、「会話経由」の確認はまだ
4. **M4**：会話だけで「関節を少し動かして」のような指示が反映される（トラックC・D結合）
5. **M5**：イラスト入力から動画書き出しまで、会話を主な操作手段として一気通貫で動作する（トラックE完了、ゴール達成）
