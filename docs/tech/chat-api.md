# chat-api：OLMoを使った会話アシスタントサービス

## 概要

トラックDの会話アシスタントサービス。OLMo（`allenai/OLMo-2-0425-1B-Instruct`、画像を学習していないテキストのみのLLM）をロードし、会話応答とツール呼び出し（トラックBの`/tools/call`橋渡し経由でVRM操作等を実行）を行う。CPU推論のみで動作しGPU不要。

## 構成

- `tools.py`：ツール定義（`frontend/src/toolBridge.js`のcreateToolRegistry()と一致させる必要がある）
- `tool_calling.py`：モデルの出力から`{"tool": ..., "params": {...}}`形式のJSONを抜き出す`parse_tool_call`、`/tools/call`に送る`dispatch_tool_call`
- `app.py`：`POST /chat`エンドポイント。システムプロンプトにツール一覧を埋め込み→生成→ツール呼び出しの解析→（あれば）実行→結果を踏まえた最終応答の生成、という流れ

## 動作確認

mediapipeのバージョン非互換で本物の`api`サービス（main.py）が今の環境では起動できなかったため、`/tools/call`と同じ形式で応答するモックサーバーを使って検証した。

実際に「今のポーズを教えて」という日本語の問いかけに対し、モデルが`get_current_pose`ツールの呼び出しを生成→`parse_tool_call`が正しく抽出→`dispatch_tool_call`がモックサーバーに送信→結果を受け取って最終応答を生成、という**一連の流れが動作することを確認した**。

ただし、既知の課題（zero-shot実験で判明済み）通り、パラメータの中身がハルシネーションする（`get_current_pose`は本来パラメータ不要だが`{"na": "current pose"}`のような架空の値を生成する）ことも再確認した。実害はない（フロントエンド側の`get_current_pose`ハンドラはパラメータを無視する実装のため）が、ファインチューニングでの改善が引き続き必要。

## ファインチューニング

`generate_finetune_dataset.py`で合成データ（85件、自己生成のみ、外部データ不使用）を作り、`finetune_olmo.py`でLoRA（Low-Rank Adaptation、全体ではなく小さな追加行列だけを学習する効率的な手法）によりOLMoをファインチューニングした。RTX 5070（WSL2）で学習、学習対象パラメータは全体の0.14%（約210万個）のみ。

### 遭遇したバグ：曖昧な表現に対するランダムな正解ラベル

当初、「headを縦方向に少し回転させて」のような曖昧な表現に対し、角度(amount)をランダムに割り当てていた。これだと同じ表現が呼び出しごとに違う正解ラベルを持つことになり、モデルが学習しようがない矛盾したデータになっていた（学習は収束したが損失が0.017止まりだった）。「少し／そこそこ／大きく」という表現ごとに固定の角度を対応付けるよう修正したところ、損失が0.0002まで収束するようになった。

### 評価結果

`evaluate_finetune.py`で、学習に使っていないseedで生成したheld-outデータを使い、ファインチューニング前後の精度（ツール名・パラメータの完全一致率）を比較した。

| | 精度 |
|---|---|
| ファインチューニング前（zero-shot） | 10.6% |
| ファインチューニング後（LoRA） | **100.0%** |

わずか85件の合成データ・LoRAという軽量な手法でも、この種の限定的なタスク（決まったツール一覧からの選択とパラメータ抽出）には十分な効果があることを確認した。

## 追記：ファインチューニング済みモデルでの実サービス動作確認

`app.py`が環境変数`CHAT_API_LORA_ADAPTER_DIR`でLoRAアダプタを読み込めるようにし、モックサーバー相手に実際の`/chat`エンドポイントで動作確認した。

- 「頭を縦方向に大きく回転させて」→`{"tool": "set_bone_rotation", "params": {"bone_name": "head", "x": 1.2, "y": 0.0, "z": 0.0}}`（bone_name・軸・角度すべて正確）
- 「今のポーズを教えて」→`{"tool": "get_current_pose", "params": {}}`（正確）

評価スクリプトでの100%という数値が、実際のサービス経路でも再現することを確認した。ツール実行結果を踏まえた最終応答の自然文生成（followup）は、1.5Bという小規模モデルの限界でやや不自然になることがあるが、ツール呼び出し自体（本質的な機能）は正確に動作する。

## Docker化

`avatar-api`と異なりGPU（CUDAコンパイラ）に依存しないため、Docker化のハードルが低い。CPU版PyTorch（`--index-url https://download.pytorch.org/whl/cpu`）を使いイメージサイズを抑えている。`docker-compose.yml`に追加し、実際にビルド・起動・`/chat`エンドポイントへのリクエストが動作することを確認した。

コンテナ間通信のため、`CHAT_API_TOOLS_BASE_URL`は`http://api:8080`（サービス名）を指定する。ファインチューニング済みLoRAアダプタは学習成果物（大きなバイナリ）のためGit管理対象外とし、`chat-api/lora_adapter/`に配置した上でdocker-compose.ymlのコメントアウトを外してマウントする運用とした。

## フロントエンドUI連携と相対指示への対応（2026-09-10）

ユーザーから「左手を上げる」のような部位ごとの細かい指示をしたいという要望を受け、`set_bone_rotation`ツールが最適と判断し、これまでcurl・モックサーバーでしか確認していなかったchat-apiをフロントエンドの会話UI（`ChatBox.jsx`、「会話でポーズを調整」）から使えるようにした。`set_bone_rotation`は関節ごとに独立して動くため、「左手を上げて」→「足も上げて」のように異なる部位への指示を連続で出しても干渉せず積み重なる。

### 相対指示（「もっと」「元に戻して」）への対応

続けて、「もう少し」のような**直前の自分の指示を踏まえた相対的な追加指示**にも対応させた。

1. **会話履歴の形式を修正**：フロントエンドが次のターンでモデルに渡す「AI応答」を、自然文の返答ではなく学習時と同じツール呼び出しの生JSON形式に統一した（`ChatBox.jsx`）。自然文だと直前の自分の出力を正確な数値として参照できないため
2. **学習データに2ターン会話を追加**：全17ボーン×3軸それぞれについて「(部位)を(軸)方向に少し回転させて」→「もっと動かして」（同じ軸に+0.3）／「元に戻して」（全軸0）という2ターンの会話例を102件追加（`generate_relative_adjustment_examples()`）

187件（85+102）で再学習した結果、未学習seedでの評価が**5.9%→100.0%**。さらに、学習データに一切ない言い回し（「もっと動かして」等のテンプレートと一致しない、単語単体の「もっと」）でも正しく前回値+0.3に増分できることを確認し、単純な暗記ではなく汎化していることを確認した。

### 実際のUI経由での動作確認

docker-compose.ymlでLoRAアダプタ（`chat-api/lora_adapter`）を有効化し、Playwrightで実際のUIから「左手を横方向に少し回転させて」と送信 → VRMの`leftHand`ボーンのY軸回転が実際に0→約0.3に変化することを確認した（ツール呼び出し→`/tools/call`→WebSocketブリッジ→ブラウザでの実行、という一連の流れが実際に機能している）。

**判明した制約**：CPU推論のため1ターンあたり90〜130秒程度かかる（ツール呼び出し検出＋結果の自然文説明の2回の生成のため）。「複数の指示を素早く積み重ねる」という当初の使い方には現状やや遅い。

### 応答速度の改善

`max_new_tokens`の既定値を200→80に削減（ツール呼び出しJSONは長くても数十トークンで収まるため）。実際のUI経由での往復時間が**90〜130秒→約49秒**に改善した。

トレードオフとして、結果を踏まえた最終応答（自然文の説明）が`{"ok": true}`のようなJSON的な短い出力になりやすくなった。ファインチューニングデータがツール呼び出しJSONのみで構成されており、「結果を踏まえて自然文で返答して」というfollowup用の指示自体は学習データに一度も登場しないため、モデルが最も慣れたJSON的な出力パターンに引っ張られると考えられる。ツール実行自体（本質的な機能）への影響はない。自然文の質を上げたい場合は、followup用の短い自然文応答パターンも学習データに加えることが今後の選択肢になる。

## 対象ボーンを指まで含む全55種類に拡張（2026-09-10）

ユーザーから「関節点を今後増やせるか」という質問を受け、VRM humanoidがサポートする
ほぼ全ボーン（指の各関節・つま先・肩甲骨・上胸・あご・目を含む55種類）まで拡張した。

- `generate_finetune_dataset.py`のBONE_NAMES_JAを17→55種類に拡張（指ボーンはタイプミス防止のため
  ループで機械的に生成、`_finger_bone_names_ja()`）
- 学習データが187件→529件に増加
- フロントエンド（`vrmPose.js`のBONE_NAMES、`get_current_pose`・キーフレーム記録が使う対象ボーン）も
  同じ55種類に拡張し、Pythonの語彙表と完全一致することを確認済み

### 結果：held-out評価は100%だが、テンプレートに忠実な言い回しに限る

`evaluate_finetune.py`（学習と同じテンプレート構造で生成した未学習seedのデータ）では
**4.3%→100.0%**。しかし、これは「○○を○○方向に○○回転させて」という学習テンプレートと
同じ文型でのみ検証している点に注意が必要と判明した。

**学習テンプレートに近い言い回し**（「左人差し指の根元を縦方向に少し回転させて」等、
関節名を正確に指定）では実際にAPI経由でも100%正確に動作することを確認した。

**カジュアルな言い回し**（「左手の人差し指を曲げて」のように動詞を変える、どの関節か
曖昧にする等）では、存在しないボーン名（`leftHandDistal`等、学習した部位名の断片を
それらしく組み合わせた架空の名前）を出力することがあった。「あごを開けて」への応答が
`get_current_pose`を誤って選ぶケースもあった。テンプレートと違う動詞・言い回しへの
汎化はまだ弱いため、狙った通りに動かない場合は「○○を○○方向に○○回転させて」という
学習時に近い言い方を試すとよい。

## 今後の課題

- 本物のapiサービスとの統合確認（mediapipeのバージョン固定・動作確認が別途必要）
- チャットの会話履歴管理（現状は毎回全メッセージをリクエストで渡す設計）
- **言い回しのバリエーションを増やす**：「回転させて」以外の動詞（曲げて、伸ばして等）や、
  関節を曖昧に指定した場合のデフォルト挙動（例：関節を省略したら根元を対象にする）を
  学習データに加えると、カジュアルな言い回しへの汎化が改善する見込み
- ツール実行結果を踏まえた最終応答の自然文生成の質（`max_new_tokens`削減後、JSON的な短い出力に寄りやすい。followup用の自然文応答パターンを学習データに加えると改善が見込める）
- 応答速度：49秒まで改善したが、複数指示を素早く積み重ねたい用途にはまだ余地がある。GPU推論への切り替え（WSL2、`avatar-api`と同じ構成）も選択肢だが、「GPU不要」というchat-apiの利点を失う判断になるため要検討
